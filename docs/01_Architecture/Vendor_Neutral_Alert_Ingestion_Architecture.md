# AISOP Vendor-Neutral Alert Ingestion & Adapter Architecture

## 1. Executive Summary

AISOP (AI-Assisted Security Operations Platform) is designed as a vendor-neutral, local-first investigation platform. It ingests security alerts and supporting telemetry from heterogeneous enterprise security tools, normalizes them into a canonical investigation schema, and provides analysts with evidence-grounded investigation workflows.

This document describes the vendor-neutral alert ingestion architecture, canonical schema specifications, adapter protocols, deduplication guarantees, and database persistence models.

## 3. Data Taxonomy & Core Distinctions

AISOP enforces strict conceptual separation between four distinct security entities:

1. **Security Alert:** A high-level detection finding generated by an upstream detection engine or security tool (e.g. CrowdStrike Falcon malware detection, Suricata network intrusion alert, AWS GuardDuty anomalous credential usage).
2. **Raw Telemetry:** Low-level, granular operating system or network logs (e.g. Windows Sysmon Event ID 1 process creation, Linux auditd syscall, Zeek network flow). High-volume and largely benign.
3. **Evidence:** A cryptographically hashed (SHA-256) immutable artifact stored in the platform with chain-of-custody, whether originating as an alert or raw telemetry.
4. **Investigation:** A structured, case-scoped analytical container linking alerts, evidence, atomic entities, threat intelligence, timeline, and AI hypotheses.

## 4. Canonical Alert Specification (`CanonicalAlert`)

The `CanonicalAlert` schema (`app.schemas.alert`) establishes the platform contract:

```python
class CanonicalAlert(BaseModel):
    id: UUID
    source_type: str
    source_alert_id: str
    title: str
    description: str | None
    severity: Literal["informational", "low", "medium", "high", "critical", "unknown"]
    vendor_severity: str | None
    category: Literal[
        "malware", "initial_access", "execution", "persistence",
        "privilege_escalation", "defense_evasion", "credential_access",
        "discovery", "lateral_movement", "collection", "exfiltration",
        "command_and_control", "impact", "suspicious_activity",
        "policy_violation", "system_anomaly", "other"
    ]
    provider: str
    status: Literal["new", "triaged", "investigating", "closed", "suppressed"]
    timestamp: datetime
    ingested_at: datetime
    mitre_attack: list[MitreAttackReference]
    entities: list[AlertEntity]
    observables: list[AlertObservable]
    host: HostEntity | None
    user: UserEntity | None
    process: ProcessEntity | None
    network: NetworkEntity | None
    file: FileEntity | None
    dns: DnsEntity | None
    registry: RegistryEntity | None
    raw_ref: str
    raw_payload_summary: str | None
    custom_fields: dict[str, Any]
```

### Downstream Compatibility via `to_canonical_event()`
Every `CanonicalAlert` seamlessly projects into a `CanonicalEvent`:
- `event_id`: Upstream vendor alert ID (`source_alert_id`).
- `event_type`: Normalized alert category (`alert.{category}`).
- `action`: `"alert_triggered"`.
- `severity`: Normalized severity mapped to standard event levels.
- `custom_fields`: Preserves original alert metadata, MITRE techniques, observables, and vendor attributes.

## 6. Ingestion Pipeline & Transactional Invariants

The `AlertIngestionService` enforces strict data integrity:
1. **Cryptographic Hashing:** Computes SHA-256 digest of every incoming alert payload.
2. **Batched Existence Lookup:** Checks for existing hashes in chunks of 1000 records ($O(\lceil U / 1000 \rceil)$ query complexity).
3. **In-Memory Classification:** Accurately classifies alerts into new unique items vs. existing database records vs. intra-batch duplicates.
4. **Atomic Savepoint Isolation:** Normalization and database insertion of `RawEvidence`, `NormalizedEventModel`, and `ExtractedEntityModel` are enclosed in nested savepoints (`async with session.begin_nested()`).
5. **Zero Orphaned Evidence Guarantee:** If an alert fails normalization or entity insertion, the savepoint rolls back cleanly without leaving partial records.

## 7. REST API Endpoints

- `POST /api/v1/alerts/ingest`: Accepts `AlertIngestRequest` (max 1000 alerts per batch, 128 KB payload ceiling), protected by API key / Bearer authentication. Returns `AlertIngestResponse` with batch tracking UUID, normalized count, skipped duplicate count, and alert UUIDs.
- `GET /api/v1/alerts/adapters`: Returns all registered adapters, supported severity levels, and classification categories.
