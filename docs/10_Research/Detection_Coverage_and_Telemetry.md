## What this is for
A rule can only fire if the telemetry it reads exists. Before a pilot, a detection engineer checks that each source below is collected and forwarded in the form the rules read. This document lists the rules that exist and the logging they depend on; it is **not** a claim that a technique is detected.

Measured result, for context (`docs/10_Research/Detection_Engineering_Evaluation.md`): on the held-out half of public attack captures labelled by their own authors, the rules recovered 11 of 34 documented techniques (32%; interval about 19% to 49%). Lateral movement, Kerberos and in-memory techniques are mostly not covered, and several captures lacked the telemetry altogether.

The table has 39 rules covering 36 techniques: T1003.001, T1003.002, T1003.003, T1012, T1021.002, T1021.006, T1037.001, T1047, T1053.005, T1055, T1059.001, T1069.001, T1069.002, T1070.001, T1087.002, T1105, T1136.001, T1140, T1197, T1218.001, T1218.002, T1218.003, T1218.004, T1218.005, T1218.007, T1218.008, T1218.009, T1218.010, T1218.011, T1220, T1490, T1518, T1543.003, T1547.001, T1548.002, T1562.002.

Notes a detection engineer should act on:
- Most rules read **process creation with the command line**. On Windows that means Sysmon event 1, or Security event 4688 with the policy "Include command line in process creation events" enabled. One public capture shows an attacker turning that policy off, and the table has a rule for it (`EP-T1562.002-LOGGING-DISABLE-COMMAND`), but the change is only visible if it was logged before it took effect.
- Sysmon event 10 against lsass.exe is excluded by many default configurations to reduce volume. If it is excluded, the LSASS memory rule cannot fire.
- Command-line rules show that a command was run. They do not show who ran it, whether it succeeded, or why; each rule's limitation is stated below.
- Normalised records keep a fixed whitelist of typed source fields (`source_fields`, 300 characters each). Fields outside that list are not visible to any rule.
