# Real-format ingestion result (2026-11-23)

Purpose: answer "your ingestion was only ever tested on data you wrote" with a measurement on data the project did not write.

## Data
Two small attack-simulation datasets from OTRF Security-Datasets (MIT; https://github.com/OTRF/Security-Datasets): `cmd_sharpview_pcre_net` (267 records) and `psh_powershell_httplistener` (110 records). Lab-generated by the dataset authors on a simulated Active Directory environment, not customer data. Flat JSON lines from a Windows event forwarder with Sysmon and Security channels. Stored outside the repository in `D:\AISOP-Reference-Data\otrf_samples_20261123\`; a 10-record unmodified excerpt is in `datasets/samples/public/` with attribution.

## Result before any change (as-is)
| File | Records | Accepted | Rejected |
|---|---|---|---|
| cmd_sharpview_pcre_net | 267 | 0 | 180 `NO_ADAPTER` (Sysmon), 87 `TIMESTAMP_MISSING_OR_INVALID` (Security) |
| psh_powershell_httplistener | 110 | 0 | 104 `NO_ADAPTER`, 6 `TIMESTAMP_MISSING_OR_INVALID` |
The system rejected every real record, safely (rejections are recorded with the raw digest, not dropped). The earlier claim "8 adapters" meant sample-shaped inputs only.

## Change (four small edits, no new component)
`sysmon_adapter.py`: recognise the forwarder's `Channel` / `SourceName` marker; read `Hostname` as the host. `windows_security_adapter.py`: read the top-level `TimeCreated` / `@timestamp`; read `Hostname`. `correlation/normalize.py: _event_data`: a record carrying `EventID` plus a `Channel` or `SourceName` is its own event data (found afterwards: without this the correlator read an empty event for flat records, so process GUIDs, DNS names and logon ids were silently missing). A flat record with no Sysmon or Security marker is still not claimed (tested).

## Result after
| File | Records | Accepted | Rejected | Evidence clusters | Incidents | Sufficiency of incidents | Time |
|---|---|---|---|---|---|---|---|
| cmd_sharpview_pcre_net | 267 | 267 | 0 | 42 | 12 | 12 LIMITED | 0.18 s |
| psh_powershell_httplistener | 110 | 110 | 0 | 17 | 8 | 8 LIMITED (7 LIMITED and 1 SUFFICIENT before the vantage rule) | 0.07 s |
Two source types (sysmon, windows_security) were normalised from real exports. Every raw record is kept with its own digest. (After only the first three edits the figures were 41/11/11 LIMITED and 17/17/17 LIMITED; the fourth edit changed them.)

## The one SUFFICIENT verdict, examined, and what was done about it
After the fourth edit one incident became SUFFICIENT. It consisted of two Sysmon records on one host: a registry key event (event 12) and a registry value set (event 13) by the same `svchost.exe` process instance, joined by a STRONG process-GUID link. Both came from the same sensor, and the activity is ordinary Windows behaviour.
- The gate was working as designed: independence meant *a different raw record linked by a specific or strong artefact*, not *a different sensor*.
- That was a real design limit, so it was addressed (ADR-017, implemented 2026-11-24): corroboration now needs more than one known vantage point across the chain of specific links, otherwise the verdict is capped at LIMITED with `SAME_VANTAGE_ONLY`. On the same data all 20 incidents are now LIMITED (12 and 8), and the three synthetic envelope scenarios stay SUFFICIENT because their records span several vantage points.
- The cap was designed from this finding and then checked against the same data, so this is a demonstration of the mechanism, not an independent validation of it.

## Second real source: SSH server log (2026-11-24)
Data: the public Loghub OpenSSH sample (2,000 raw sshd syslog lines from a lab server, https://github.com/logpai/loghub). Its README states the logs are freely accessible for research and asks users to cite its papers; cite them from the README. The data is kept outside the repository (`D:\AISOP-Reference-Data\loghub_openssh_20261124\`) and is not redistributed here.
- **No year in syslog.** A syslog line has no year and AISOP never invents a timestamp. A bare line is rejected (`NOT_AN_OBJECT`), an object with no time is rejected (`TIMESTAMP_MISSING_OR_INVALID`), and the new converter `backend/scripts/syslog_to_records.py` requires an explicit `--year`, marks every record `year_assumed`, and counts year rollovers. The year used here (2015) is an assumption.
- **Result:** 2,000 of 2,000 records accepted from one source type (`linux_auth`), every timestamp flagged as assumed; 852 evidence units; 23 incidents, all LIMITED (18 with `SAME_VANTAGE_ONLY`, 5 `REPEATED_OBSERVATION_ONLY`, 5 `UNCORROBORATED_QUESTION`, 1 `EVIDENCE_TRUNCATED`). A flood of failed logins seen by one sensor is one witness, and the gate says so. Processing time 11.7 s for 2,000 records.
- **Defects found by the real data and fixed in the adapter:** an address with a trailing colon ("Received disconnect from 1.2.3.4: 11") was taken as an address; a hostname after "getaddrinfo for" was taken as a user (80 lines); no address or user was read from `rhost=`, `[IP]`, `by IP`, `Invalid user NAME` and `user=NAME` lines. Before: 615 users and 1,116 addresses parsed (some malformed). After: 1,137 users and 1,732 valid addresses.
- **Limits:** one dataset from one lab server; the year is assumed; no ATT&CK rule fires for this source (the brute-force rule is built for Windows security events only, which is a real gap); 2,000 records took 11.7 s before and 3.1 s after the 2026-11-24 speed-up (identical output, see `docs/05_Backend/Stage5_Performance_Report.md`); the API accepts at most 1,000 evidence rows per run (ADR-010), so a log this size is split into runs.

## What the result does and does not show
- Shows: the pipeline now ingests two real forwarder-style Windows sources end to end on data the project did not author; all 20 incidents are LIMITED after the vantage rule (one was SUFFICIENT before it; see above), which is conservative for a single-host lab attack.
- Does NOT show: that the verdicts are right (no labels), that the ATT&CK rules cover this data (no rule fired on either file), or that other vendors' formats work (only this forwarder shape was tested; Suricata EVE real samples were not obtained).

## Limitation found by this test: over-merging of distinct events (safe direction)
225 of 267 records in the first file collapsed into duplicate clusters. The near-duplicate rule keys on host, event type and the extracted entities within 2 seconds, and the entity set does not include every distinguishing field. Examples inside single clusters (measured after the fourth edit): image load (event 7) 82 records in 14 merged clusters with up to 12 distinct loaded modules; process access (event 10) 49 records with 6 distinct target images; registry set (event 13) 23 records in 3 clusters with up to 6 distinct registry keys; file create (event 11) 3 records with 3 distinct file names; DNS (event 22) 2 records with 2 distinct query names (the fourth edit reduced this from 3, the remainder was not investigated).
- Direction of the error: **safe**. Merging lowers the count of independent evidence units, so it can only make a verdict more cautious, never inflate corroboration. Raw records are all preserved.
- Cost: resolution is lost (three different DNS lookups count as one unit), and it may be one reason for LIMITED verdicts.
- Not changed now: adding distinguishing fields as entities would also create new links and change verdicts everywhere, which is a semantic change that needs its own evaluation and ADR. Listed as future work.

## Reproduce
Download the two zips from the repository paths above, extract, run `analyze()` from `app.modules.correlation.workflow` over the JSON lines. Tests: `backend/tests/unit/test_real_format_flat_forwarder_ingestion.py`.
