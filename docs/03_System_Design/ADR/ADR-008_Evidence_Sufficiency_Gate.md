---

## 1. Context
AISOP validates model output after the fact (3-tier claim grounding, epistemic categories, deterministic fallback in `modules/ai/guardrails/validator.py` and the response parser). Before this decision the only pre-model decision was "zero events in scope". There was no explicit, testable, auditable determination of whether the available evidence can support an investigation, so a model could be invoked on irrelevant, unverifiable, truncated or contradictory evidence and only be corrected afterwards. The first revision of this ADR also treated *distinct* events as corroboration; review showed that host-only or user-only links, events from one raw record and near-duplicates produced false SUFFICIENT outcomes (5 of 11 development predictions rested on host/user links).

## 2. Decision
1. Add a **pure, deterministic, versioned rule gate** (`suff-v2`) that evaluates the already-built `InvestigationContext` and returns `SUFFICIENT`, `LIMITED` or `INSUFFICIENT` with fixed-vocabulary reason codes and event UUID references.
2. **INSUFFICIENT forbids any model invocation** and returns an auditable abstention (no claims, no hypotheses, no verdict). **LIMITED** allows a bounded investigation: a trusted fixed-text limitation notice is added to the prompt; inference claims that rest on fewer than two **independent evidence clusters** are demoted to analyst review by the validator; and a coded disclosure (`EVIDENCE_SUFFICIENCY[suff-v2]=LIMITED: <codes>`) is appended to the final output's `uncertainty_and_data_gaps` (`apply_sufficiency_disclosure`), so it reaches the analyst-facing report and not only the prompt.
3. Classification depends on the investigation question (root anchor event, else target hosts and time window), on the **relevance** of each evidence unit to it, and on **reliability** (valid raw-evidence digest, de-duplication, independence). There is no universal event-count threshold.
4. The gate **fails closed**: any exception yields INSUFFICIENT (`GATE_EVALUATION_ERROR`); an exception can never permit a model call.
5. A single choke point, `GatedGenerator.generate`, is the only production code that calls `LLMProvider.generate`; both production invocation sites (`investigation_service`, `case_service`) run the gate first and use it, as does the multi-source workflow (ADR-009). An architecture test fails on any other `.generate(` call. No configuration, environment or API switch disables the gate; only the evaluation harness (gate-off ablation arm) can bypass it and that module is not imported by production code.
6. The evaluation capture harness (`backend/scripts/capture_live_fixtures.py`) calls Ollama directly, so it applies the same gate by default and requires the explicit `--gate-off-ablation` flag (recorded in its batch summary) to bypass it.
7. The assessment is recorded in the **existing** case audit schema (`case_audit_events.details`, JSONB/JSON): no migration, no new audit action, no change to `InvestigationContext` / `StructuredInvestigationOutput` hash semantics (the disclosure is appended to the validated output before its digest is computed).

## 3. Independence (the definition the rules use)
`app/modules/evidence/independence.py` defines, once:
* **Evidence clusters**: events collapse into one evidence unit when they are the same event, share the same *attested* raw-evidence digest (one raw record parsed into several events), have identical content, or are near-duplicates (same identity and entities within 2 seconds, same outcome). Unverifiable digests (missing, malformed, all-zero) never merge events.
* **Link strength** of a shared entity (adapted from AiSOC's attack-chain link tiers): STRONG (logon session, process GUID); SPECIFIC (file hash, domain, file path, registry key, URL, e-mail, public IP address); WEAK (host, user, process name, internal IP).
* **Independent corroboration** of the question = a *different, attested* evidence cluster joined to the anchor by a STRONG or SPECIFIC link. Weak-only relationships are context: they do not corroborate and are disclosed as `WEAK_LINK_ONLY`.

## 4. Rules (version `suff-v2`)
INSUFFICIENT: `NO_EVIDENCE`, `NO_RELEVANT_EVIDENCE`, `GATE_EVALUATION_ERROR`. LIMITED: `EVIDENCE_TRUNCATED`, `ROOT_ABSENT`, `ROOT_PROVENANCE_MISSING`, `PROVENANCE_UNVERIFIED_ALL`, `UNCORROBORATED_QUESTION`, `TEMPORAL_ANOMALY`, `CONTRADICTORY_EVIDENCE` (opposite outcomes of the same logical event within 2 s, or conflicting digests for the same event), `MISSING_REQUIRED_FIELD:<entity type>`. Disclosure only: `PROVENANCE_PARTIAL`, `DUPLICATE_EVIDENCE_COLLAPSED`, `IRRELEVANT_EVIDENCE_EXCLUDED`, `WEAK_LINK_ONLY`. Thresholds are conditions on existing fields, not tuned scores.

### Rules not adopted (evaluated against the code first)
* **Source-recognition rule**: `ContextEventItem` carries no source type; adding one would alter context hash semantics. Reliability is expressed through provenance and independence.
* **Injection-pattern rule**: the application defends by structural isolation (XML escaping, role separation) and has no detector to reuse; a new heuristic regex set would add false positives and a weaker second mechanism. The gate never interprets evidence text; tests assert injected text neither changes the verdict nor appears in the assessment.

## 5. Alternatives considered
(A) LLM self-assessment of sufficiency: rejected (model-controlled, non-deterministic, injectable). (B) A numeric evidence score with a tuned threshold: rejected (arbitrary, hard to audit). (C) Post-hoc guardrails only (status quo): cannot prevent unsupported invocations. (D) New audit action plus migration: unnecessary. (E) Learned/probabilistic sufficiency estimator: deferred (needs labelled data and a literature basis). (F) Make unverified provenance INSUFFICIENT: not chosen (it would change the offline baseline's behaviour; unverified provenance is LIMITED and disclosed).

## 6. Consequences
Positive: deterministic, explainable, testable pre-model decision; auditable abstention; no model cost on unusable evidence; one independence notion across gate, validator and correlator. Negative: more LIMITED outcomes (more analyst review); the rule table must be maintained and versioned; the gate does not replace claim grounding. Future compatibility: adding fields to `InvestigationContext` or the output requires a hash-versioning ADR; the gate API is stable for later milestones (deterministic correlation and ATT&CK mapping add entity and link types the corroboration rule can use).

## 7. Security implications
Fail-closed behaviour; no bypass switch; assessment contains only enums, counts and event UUIDs; audit write failure still suppresses the result; assessment bound to the context SHA-256. Abuse considerations: an attacker able to degrade provenance or inject contradictory events can force LIMITED/abstention (availability risk, monitor reason-code rates); forged shared public IPs/domains/hashes can create a specific link (auditable through raw digests, not preventable here); duplicate or correlated evidence can no longer inflate corroboration.

## 8. Evaluation approach
A hash-locked set of 115 derived cases (development 67, held-out 48) (`datasets/sufficiency_eval`, outside `datasets/ground_truth` whose loader scans recursively): opaque case ids, split stratified by scenario family (every family appears in both development and held-out; no base scenario in both), transforms include near-duplicates, host/user-only links, same-record pairs and an `independently_corroborated` variant (a second sensor, distinct raw record, shared domain), which supplies positive examples because the original scenario telemetry has no independent corroboration (a limitation to disclose: those positives are synthetic by construction). Ground-truth labels are owner-authored (`labels.json`, never generated by code; a second reviewer where possible; ambiguous cases left null and excluded). Metrics: confusion matrix, per-class precision/recall, macro F1, false-sufficient and false-insufficient rates with Wilson intervals, abstention rate, coverage versus risk (two operating points), model-invocation prevention, evidence-reference validity, weighted kappa between reviewers, and a gate-on/gate-off ablation with a call-counting scripted provider. Thresholds are tuned on development only; held-out is evaluated once with an explicit flag. Status: accuracy metrics are PENDING owner labels (UNVERIFIED). This evaluates engineering behaviour on synthetic cases; it does not establish research novelty or real-world performance.

## Stage 5 revision: `suff-v3` (2026-11-12; status unchanged: PROPOSED, owner approval pending)
Adversarial testing of the implemented gate (`backend/tests/unit/test_stage5_adversarial.py`) found two defects in the independence rules and corrected them. This changes behaviour, so the rule version is `suff-v3` (`SUFFICIENCY_RULE_VERSION`); stored results carry the version they were produced with.
* **D1 - repeated observations are not corroboration.** Two evidence clusters of the same observation class (same `source_identifier`, `event_id`, `event_type`, `action`) no longer corroborate each other even when their raw digests differ and they are seconds or hours apart and share a specific artefact. Such a pair yields `UNCORROBORATED_QUESTION` plus the new disclosure code `REPEATED_OBSERVATION_ONLY` (`sufficiency_gate.py: same_observation_class, corroborates`). Rationale: a re-emitted, replayed or forged copy of one observation, or the same sensor repeating itself, is not a second kind of proof.
* **D2 - placeholders are not artefacts.** A shared value that carries no information (`unknown`, `-`, `null`, `N/A`, `localhost`, zero or uniform hash, malformed hash, domain without a dot, e-mail without `@`, zero process GUID, SYSTEM/service logon sessions) is a WEAK link whatever its entity type (`independence.py: is_informative_value, entity_link_strength`). Comparison of domains, hashes, e-mail, addresses and sessions is case-insensitive (`canonical_entity_value`).
* Unchanged: duplicate/near-duplicate clustering, link tiers, fail-closed behaviour, the fixed reason vocabulary (one code added), the dataset and hash lock. The development split's predicted distribution is identical under `suff-v2` and `suff-v3` (11/52/4), so no development case exercises these defects; they are covered by unit tests, and the held-out split lacks several independence probes (see `docs/10_Research/Evaluation/Stage5_Evaluation_Report.md`).
* Known limit (R1): two different kinds of event sharing a specific artefact still corroborate; a compromised or spoofing source that fabricates both can obtain SUFFICIENT. Requiring distinct sensor families needs `source_type` in the gate context (PROPOSED).
